# PRD 拆分工作流

输入：`$ARGUMENTS`
- 第一个参数：PRD Markdown 文件路径（必填，缺失时询问用户）
- 第二个参数：输出目录（可选，默认 `./specs`）

## 步骤

### 1. 阅读并理解 PRD
- 完整读取 PRD 文件，不要只读一部分。
- 识别出**相互独立、可单独开发交付**的需求单元（功能模块/用户故事/特性）。
- 拆分粒度：一个需求 = 一个可以独立设计、开发、验收的功能。太大（跨多个模块）就继续拆，太小（只是一个字段）就合并。
- 全局性内容（背景、术语、通用非功能需求）不单独成文件夹，写入 `00-overview/README.md`。

### 2. 先输出拆分清单让用户确认
用表格列出：序号、文件夹名、需求名称、一句话描述、依赖的其他需求。
等用户确认或调整后再生成文件（用户明确说“直接生成”时可跳过确认）。

### 3. 生成目录结构
文件夹命名：`<两位序号>-<英文短横线名称>`，序号按建议开发顺序（被依赖的在前）。

```
specs/
├── 00-overview/
│   └── README.md          # PRD 背景、术语、全局约束、需求索引与依赖关系
├── 01-user-login/
│   ├── requirements.md
│   ├── design.md
│   └── tasks.md
├── 02-xxx/
│   └── ...
```

如果输出目录已存在同名文件夹，先告诉用户，不要直接覆盖。

### 4. 各文件内容模板

#### requirements.md
```markdown
# <需求名称> - 需求说明

> 来源：<PRD 文件名> § <对应章节>

## 背景与目标
<为什么做，解决什么问题>

## 用户故事
- 作为 <角色>，我希望 <功能>，以便 <价值>

## 功能需求
### FR-1 <名称>
<描述>

**验收标准**
- WHEN <条件> THEN 系统 SHALL <行为>
- ...

## 非功能需求
<性能、安全、兼容性等；没有则写“无特殊要求”>

## 范围外
<明确不做的内容>

## 依赖
<依赖的其他需求文件夹 / 外部系统>

## 待确认问题
<PRD 中模糊或缺失的点；没有则省略本节>
```

#### design.md
```markdown
# <需求名称> - 技术设计

## 概述
<整体方案一段话>

## 架构 / 流程
<模块关系或流程，可用 mermaid>

## 数据模型
<表结构 / 实体 / 字段>

## 接口设计
<API：方法、路径、请求、响应、错误码>

## 前端 / 交互（如适用）
<页面、组件、状态>

## 异常处理
<边界情况与错误处理>

## 测试策略
<单测、集成测试要覆盖的点>
```
设计内容要具体到可以直接开发；PRD 未提供的技术细节可以做合理假设，但要标注“（假设）”。如果项目里已有代码，先看现有技术栈和约定，设计要与之一致。

#### tasks.md
```markdown
# <需求名称> - 任务清单

> 状态说明：`[ ]` 未完成，`[✅]` 已完成

- [ ] 1. <任务标题>
  - <具体做什么>
  - 涉及文件：<路径（如已知）>
  - 对应需求：FR-1
- [ ] 2. <任务标题>
  - [ ] 2.1 <子任务>
  - [ ] 2.2 <子任务>
- [ ] 3. 编写测试并通过
```
任务规则：
- 每一项都必须以 `- [ ]` 开头（子任务缩进两个空格，同样用 `- [ ]`）。
- 每个任务是一次可完成、可验证的编码动作（大约 0.5–4 小时的工作量）。
- 按执行顺序排列，先数据层/后端，再接口，再前端，最后测试与联调。
- 每个任务都标注“对应需求”，保证 requirements.md 中每个 FR 至少被一个任务覆盖。
- 只写开发任务，不写“开会”“评审”这类非编码事项。

### 5. 收尾
- 生成 `00-overview/README.md`：PRD 摘要 + 需求索引表（链接到各文件夹）+ 依赖关系（mermaid 图）+ 汇总的待确认问题。
- 向用户报告：生成了哪些文件夹、总任务数、需要确认的问题。
- 提示后续可用 `/ewb:task-dev <文件夹>` 按 tasks.md 进行开发。
